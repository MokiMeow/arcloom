# Arcloom interface system

The interface is an operational investigation workspace, with an enterprise
product landing page and a separate authenticated application. Reports,
execution approvals, runner observations and accepted evidence remain distinct.
Application state comes from actual API records and graph queries.

## Visual foundation

Use a bright pale-blue landing canvas, an interactive evidence-to-memory workbench, generous rounded
product sheets, a floating glass navigation pill and large black headings. The
authenticated workspace uses a light collapsible sidebar, white bordered cards,
neutral analytical charts and near-black primary buttons. Restrained sky-blue
selection and text-labelled state colors connect the two surfaces. The original
arc-strand Arcloom mark with its blue memory point and matching SVG favicon express connected memory.
Locally bundled Manrope Variable supplies body, controls and headings; monospace
is reserved for identifiers, hashes and technical metadata.

The three user-selected Tessory references take priority: Haoqi's archived chrome
and sky-blue presentation, Kaze's rounded/cloud atmosphere and floating navigation,
and Dashboard1's broad analytical workspace conventions. Inspect their current
records and available previews before extending the direction. See
[references and rights](docs/design-references.md) for actual inspection evidence
and source limits. All Arcloom layouts, illustrations and interface code are
original. No proprietary Dashboard1 source or creator screenshots are bundled.

## Operational behavior

Prioritize the investigation queue and distinguish execution approval from
evidence review. State counts identify their scope: global dashboard counts,
loaded-page filters, active-revision budgets or current findings. Do not invent
trend lines, risk scores, SLAs, customer logos or throughput metrics. An empty
workspace is a valid state with a clear report action. Graph failures fail closed.
Use server-reported time to display scope expiry; resuming scope does not renew it.

Lists support search, text-labelled states, sorting within the loaded page,
pagination and complete mobile cards. Graph nodes have both a canvas and a
searchable/paginated record list that selects the same inspector. Activity
filters operate on loaded audit records and retain cursor pagination. Native
account/report/command dialogs preserve keyboard focus and error states.

Individual accounts use email/password sign-in, explicit recovery-code saving and
private empty workspaces. Dashboard widgets can be rearranged by pointer or
keyboard, widened and reset; persist layout metadata per account, never data or
credentials. Complete technical identifiers wrap and support exact copying.

Workspace secrets stay server-side. Keep one-time credentials visible until the
user dismisses them. Respect roles and the public recorded-demo adapter. Marketing
architecture diagrams explain the product without pretending to contain live
workspace data. Capture the actual application when validating the dashboard.

## Motion and accessibility

Use short eased transitions for navigation, selection, disclosures and route
entry. The landing may animate an interactive evidence-to-memory workbench and sheet transitions; reduced-motion
users receive the same usable content and controls without animation. Keep
semantic tables, native form labels, text states, visible focus, modal focus
restoration, a skip link and named mobile navigation. Touch controls need 44px
minimum targets. Avoid clipped controls or hiding overflow as a layout repair.

Validate 320, 390, 768, 1024, 1440 and 2560px widths, long records, keyboard-only
navigation, authentication failures, role restrictions, separate approvals,
evidence verification/export, graph inspection and revision revalidation.
Automated accessibility checks supplement visual/keyboard review; they do not
establish comprehensive accessibility or physical-device coverage.
